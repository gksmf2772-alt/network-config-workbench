## 2. 수동 기능 검증

### 시나리오 1: 리포트 상세 필드에서 예외 규칙 추가
- 절차:
  1. 리포트 탭에서 핵심 보기의 상세 필드를 연다.
  2. 필드 카드 우측 상단의 규칙 추가 아이콘을 누른다.
  3. 처리 유형과 범위를 선택하고 규칙을 추가한다.
  4. 재비교 확인창에서 실행 여부를 선택한다.
- 기대 결과:
  - 규칙이 프로파일 예외 또는 필수 규칙에 저장된다.
  - 재비교를 선택하면 리포트/요약 결과가 갱신된다.
  - 재비교를 취소하면 프로파일은 저장되고 비교 상태가 stale로 표시된다.
- 실제 결과:
  - 2026-06-02 자동 테스트와 빌드 기준 통과. 실데이터 화면 확인은 다음 세션에서 필요.

### 시나리오 3: 변경 규칙 값 조건
- 절차:
  1. `A -> B`로 표시된 변경 항목에서 변경 규칙을 추가한다.
  2. 같은 필드가 `A -> B`인 경우와 `A -> C`인 경우를 비교한다.
- 기대 결과:
  - `A -> B`만 정상 처리된다.
  - `A -> C`, `A` 삭제, `B` 신규만 존재하는 경우는 같은 규칙으로 정상 처리되지 않는다.
- 실제 결과:
  - `tests/policy-coverage.test.js`의 exact value change exception 테스트 통과.

### 시나리오 4: 적용된 규칙 표시와 해제
- 절차:
  1. 리포트 상세 필드 카드에서 규칙을 추가한다.
  2. 재비교를 실행한다.
  3. 같은 상세 필드 카드가 적용 상태로 남아 있는지 확인한다.
  4. 적용 카드 우측 상단의 `-` 버튼을 누른다.
- 기대 결과:
  - 적용된 상세 필드는 초록 계열 카드 강조로 일반 필드와 구분된다.
  - 제거 가능한 profile exception이면 `+` 대신 `-` 버튼이 표시된다.
  - `-` 버튼을 누르면 해당 예외가 프로파일에서 제거되고 비교 결과가 갱신된다.
- 실제 결과:
  - `tests/summary-renderer.test.js`와 `tests/summary-analytics.test.js` 기준 통과.
  - 적용 카드/해제 버튼 형태는 검증용 카드 캡처에서 확인.

### 시나리오 5: ingress-filter 규칙 적용 표시와 해제
- 절차:
  1. `ingress-filter`가 `130 -> COD_IN`처럼 변경으로 표시된 상세 필드에서 변경 규칙을 추가한다.
  2. 재비교를 실행한다.
  3. 같은 항목이 적용 상태로 표시되고 `-` 버튼이 보이는지 확인한다.
  4. 기존에 `semantic-compare.field-difference` rule id로 저장된 규칙도 재비교 후 적용되는지 확인한다.
  5. 재비교 전이라도 아래 예외 목록에 같은 규칙이 저장되어 있으면 상세 카드가 `+` 대신 `-`를 표시하는지 확인한다.
- 기대 결과:
  - `ingress-filter` fieldSummary의 `effectiveStatus`가 `ignored`가 된다.
  - 상세 field row에 `applied: true`와 profile exception `policyId`가 포함된다.
  - 리포트 상세 카드에서는 초록 계열 적용 카드와 `-` 버튼이 표시된다.
  - stale 리포트 row에서도 저장된 예외가 있으면 `-` 버튼이 표시된다.
- 실제 결과:
  - `tests/policy-coverage.test.js`의 ingress-filter legacy exact exception 테스트 통과.
  - `tests/summary-renderer.test.js`의 중요 필드 rule id 계약 테스트 통과.
  - `tests/summary-renderer.test.js`의 저장 예외 fallback 렌더링 계약 테스트 통과.

### 시나리오 2: 객체 범위 필수 규칙
- 절차:
  1. 상세 필드에서 범위를 "이 객체만"으로 선택한다.
  2. 필수 체크 후 규칙을 추가한다.
  3. 동일 타입의 다른 객체 결과를 확인한다.
- 기대 결과:
  - 선택한 객체에만 필수 규칙이 적용된다.
  - 같은 프로파일의 다른 객체에는 객체 범위 필수 규칙이 번지지 않는다.
- 실제 결과:
  - `tests/policy-coverage.test.js`의 객체 범위 필드 정책 테스트 통과.

### 시나리오 6: 관계 그래프 라벨 토글 줄바꿈
- 절차:
  1. 리포트 탭에서 관계 그래프 영역을 연다.
  2. 우측 툴바의 `라벨` 체크박스를 확인한다.
- 기대 결과:
  - `라벨` 텍스트가 `라`/`벨`처럼 세로 줄바꿈되지 않고 한 줄로 표시된다.
  - 검색 입력, 전체 보기 버튼, 라벨 토글은 좁은 폭에서도 서로 겹치지 않는다.
- 실제 결과:
  - `tests/summary-renderer.test.js`의 그래프 라벨 CSS 계약 테스트 통과.
  - `npm.cmd run build` 통과.

### 시나리오 7: 검토 테이블 내부 스크롤
- 절차:
  1. 리포트 탭에서 검토 테이블을 연다.
  2. 검토 항목이 많은 결과를 표시한다.
  3. 테이블 영역 내부에 세로 스크롤이 생기는지 확인한다.
- 기대 결과:
  - 항목이 늘어나도 리포트 페이지 전체가 과도하게 길어지지 않는다.
  - 테이블 헤더는 내부 스크롤 중에도 상단에 유지된다.
- 실제 결과:
  - `tests/summary-renderer.test.js`의 테이블 스크롤 CSS 계약 테스트 통과.
  - `npm.cmd run build` 통과.

## 3. UI 검증

- 변경 전 캡처: 사용자 제공 화면 참고.
- 변경 후 캡처: `docs/verification/screenshots/2026-06-02/report-rule-popover/after-popover-mock.png`
- 데스크톱 확인: 헤드리스 Chrome 검증용 카드 캡처 완료.
- 상태 라벨 정렬 확인: `변경`/`동일` 라벨이 카드마다 같은 헤더 열에 표시되는지 캡처로 확인.
- 적용 카드 확인: 적용된 필드는 초록 계열 배경/테두리와 `-` 버튼으로 일반 필드와 구분되는지 캡처로 확인.
- ingress-filter 확인: 중요 필드 규칙이 적용되면 `+` 대신 `-` 버튼이 표시되는지 테스트 기준으로 확인.
- 관계 그래프 라벨 확인: 라벨 토글에 `white-space: nowrap`과 최소 폭이 적용되는지 테스트 기준으로 확인.
- 검토 테이블 스크롤 확인: 테이블 래퍼에 viewport 기준 `max-height`와 내부 스크롤이 적용되는지 테스트 기준으로 확인.
- 모바일 확인: 미수행.
- 콘솔 에러: 미수행.
- 네트워크 에러: 미수행.

- 기존 핵심 기능 1: 전체 Node 테스트 `npm.cmd test` 통과.
- 기존 핵심 기능 2: legacyCore guardrail 통과.
- 기존 핵심 기능 3: Vite production build 통과.
- 기존 핵심 기능 4: 값 조건 예외가 `A -> C`를 suppress하지 않는 회귀 테스트 통과.
- 기존 핵심 기능 5: 적용된 규칙 행이 검토 상세에서 사라지지 않고 policy id와 함께 렌더링되는 회귀 테스트 통과.
- 기존 핵심 기능 6: 기존에 잘못 저장된 ingress-filter `field-difference` 규칙이 `important-field-change`와 호환 적용되는 회귀 테스트 통과.
- 기존 핵심 기능 7: 관계 그래프 툴바 라벨 토글 줄바꿈 방지 CSS 계약 테스트 통과.
- 기존 핵심 기능 8: 검토 테이블 내부 스크롤 CSS 계약 테스트 통과.
